# 1. Purpose

This document defines the meaning, purpose, data type, nullability and validation expectations of database fields used by Niyuvia.

It supplements:

- DATABASE_DESIGN.md
- ARCHITECTURE.md
- FUNCTIONAL_REQUIREMENTS.md
- SECURITY_AND_PRIVACY_REQUIREMENTS.md

The database design document defines the overall schema. This document defines the individual fields and their expected behavior.

# 2. Global Field Conventions

| Convention | Definition |
|---|---|
| Primary identifier | UUID |
| Timestamp | TIMESTAMPTZ |
| Text | VARCHAR or TEXT |
| Boolean | BOOLEAN |
| Structured data | JSONB |
| Financial values | NUMERIC |
| Percentage scores | NUMERIC(5,2) |
| Experience | SMALLINT or NUMERIC where appropriate |
| Timezone storage | UTC |

## 2.1 Standard Timestamp Fields

| Field | Meaning |
|---|---|
| created_at | Time when the record was created |
| updated_at | Time when the record was last modified |
| deleted_at | Reserved for future soft-deletion implementation |

All timestamps must be timezone-aware.

## 2.2 Identifier Fields

Every primary identifier must:

- Be generated by the backend or database.
- Use UUID format.
- Remain immutable.
- Never be accepted as proof of authorization.

# 3. Identity Data Dictionary

## 3.1 organizations

| Field | Type | Required | Description |
|---|---|---|---|
| id | UUID | Yes | Unique organization identifier |
| name | VARCHAR(200) | Yes | Organization display name |
| slug | VARCHAR(100) | Yes | Unique URL-safe organization identifier |
| industry | VARCHAR(100) | No | Organization industry |
| website | VARCHAR(500) | No | Official organization website |
| is_active | BOOLEAN | Yes | Indicates whether organization access is active |
| created_at | TIMESTAMPTZ | Yes | Record creation time |
| updated_at | TIMESTAMPTZ | Yes | Last modification time |

Validation:

- Name must not be empty.
- Slug must be unique.
- Website must be validated as a URL when supplied.
- Organization status must be checked during authorization.

## 3.2 users

| Field | Type | Required | Description |
|---|---|---|---|
| id | UUID | Yes | Unique user identifier |
| email | VARCHAR(320) | Yes | Login or identity email |
| password_hash | VARCHAR(255) | No | Password hash when password authentication is used |
| full_name | VARCHAR(200) | Yes | User's display name |
| is_active | BOOLEAN | Yes | Indicates whether user access is active |
| email_verified_at | TIMESTAMPTZ | No | Email verification timestamp |
| created_at | TIMESTAMPTZ | Yes | Record creation time |
| updated_at | TIMESTAMPTZ | Yes | Last modification time |

Validation:

- Email must be normalized before comparison.
- Email uniqueness must be enforced.
- Passwords must never be stored in plaintext.
- Password hash must be null when authentication is entirely managed externally.

## 3.3 organization_members

| Field | Type | Required | Description |
|---|---|---|---|
| id | UUID | Yes | Membership identifier |
| organization_id | UUID | Yes | Associated organization |
| user_id | UUID | Yes | Associated user |
| role | VARCHAR(50) | Yes | Organization-level authorization role |
| is_active | BOOLEAN | Yes | Membership status |
| joined_at | TIMESTAMPTZ | Yes | Membership creation time |

Allowed roles:

- ORGANIZATION_ADMIN
- RECRUITER
- HIRING_MANAGER

Validation:

- A user must not have duplicate membership in the same organization.
- Inactive membership must not grant access.
- Role changes must be authorized and auditable.

## 8.1 resumes

| Field | Type | Required | Description |
|---|---|---|---|
| id | UUID | Yes | Resume identifier |
| organization_id | UUID | Yes | Owning organization |
| candidate_id | UUID | Yes | Associated candidate |
| original_filename | VARCHAR(255) | Yes | Original uploaded filename |
| storage_key | VARCHAR(500) | Yes | Private object storage identifier |
| mime_type | VARCHAR(100) | Yes | Detected file media type |
| file_size_bytes | BIGINT | Yes | File size in bytes |
| checksum_sha256 | VARCHAR(64) | No | File integrity checksum |
| processing_status | VARCHAR(30) | Yes | Resume processing state |
| uploaded_by | UUID | Yes | Uploading user |
| uploaded_at | TIMESTAMPTZ | Yes | Upload timestamp |

Allowed processing statuses:

- UPLOADED
- PENDING
- PROCESSING
- COMPLETED
- FAILED

Validation:

- File size must be greater than zero.
- File size must not exceed the configured upload limit.
- MIME type must be checked against file content.
- Only permitted document formats may be accepted.
- Storage keys must never expose public file access.
- Uploaded files must undergo security validation.

# 12. Common Validation Requirements

All database-backed application operations must enforce:

1. Required field validation.
2. Correct data types.
3. Maximum string lengths.
4. Valid UUID formats.
5. Foreign key integrity.
6. Organization ownership validation.
7. Valid enum or status values.
8. Appropriate timestamp handling.
9. Appropriate access authorization.
10. Protection against invalid state transitions.

Validation must exist at the API and database levels where appropriate.

# 13. Sensitive Data Classification

| Data Category | Examples | Handling |
|---|---|---|
| Identity | Name, email, phone | Restricted access |
| Recruitment | Applications, interview feedback | Role-based access |
| Documents | Candidate resumes | Private storage |
| AI | Extraction and evaluation results | Controlled access |
| Authentication | Password hashes, tokens | Strong protection |
| Audit | User actions | Restricted access |

Never log passwords, access tokens, API keys or unrestricted resume contents.

# 14. Data Dictionary Governance

Changes to database fields must be reviewed against:

- DATABASE_DESIGN.md

- SECURITY_AND_PRIVACY_REQUIREMENTS.md
- BUSINESS_RULES.md
- API specifications

Every schema change must have an associated migration.

Field definitions must remain synchronized with SQLAlchemy models and Pydantic schemas.
